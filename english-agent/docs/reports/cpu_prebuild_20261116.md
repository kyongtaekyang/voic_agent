# 영어 Agent CPU 사전 구축 보고 (2026-11-16)

GPU 여유가 약 10 GB여서(baek `app_flash.py` 30.8 GB, yang Korean_interface 7.4 GB) Moshi를 올릴 수 없습니다. 그래서 GPU 없이 할 수 있는 작업을 먼저 했습니다. **이 보고서의 내용은 사전 구축 단계이며, 단계 완료 판정을 받은 것이 아닙니다.** 모든 측정은 `CUDA_VISIBLE_DEVICES=""`로 CPU에서만 실행했습니다.

## 1. 0단계: 공용 운영 스크립트

- `ada-ops/gpu-mode`는 한국어 Agent에서 이미 만든 것을 공유합니다(프롬프트 5절: 중복 작성 금지).
- 영어 단독 프로필 `en-solo`를 `modes.conf`에 추가했습니다. 서비스 스크립트는 `ada-ops/services/en-moshi-bf16.sh`, 준비 확인은 `.ready`입니다. `gpu-mode en-solo --dry-run`을 실행했더니 "필요 24,000 MiB, 여유 10,036 MiB"로 전환을 거부했고, 이것은 의도한 동작입니다.
- realtime 모드의 `en-moshi`(Rust INT8), `en-core`, `en-web`은 아직 미구현입니다. `gpu-mode`는 미구현 서비스를 건너뜁니다.
- 포트 7101, 7102, 8998은 비어 있습니다(`ada-ops/ports.md`).
- Moshi 가중치 `kyutai/moshiko-pytorch-bf16`를 `~/.cache/huggingface`로 내려받기 시작했습니다(로그: `english-agent/logs/hf_moshiko.log`). 받기가 끝나면 GPU 사용 시간이 정해지는 대로 1단계를 바로 시작할 수 있습니다.

## 2. 2단계 사전 조사: 텍스트 토큰 추출

자세한 근거(파일과 줄 번호)는 `docs/version_check.md` 3~4절에 있습니다.

- **텍스트 토큰은 공식 WebSocket 규격(`0x02` 메시지)으로 제공됩니다.** PyTorch와 Rust 백엔드 모두 코드를 수정하지 않아도 받을 수 있습니다. 따라서 "안전 감시와 메모리 절감 가운데 선택" 문제(프롬프트 2.1절)는 생기지 않을 것으로 봅니다.
- PyTorch 서버는 같은 시점의 음성과 텍스트를 함께(음성 먼저) 보냅니다. Rust 서버는 텍스트를 먼저 보냅니다. 실제 시간 차이는 2단계에서 측정합니다.
- 여러 단어로 된 구절은 마지막 단어가 들어와야 판정할 수 있습니다. 따라서 소리가 나가기 전에 차단하려면 출력 음성 지연 버퍼가 필요할 가능성이 큽니다.

## 3. 3단계 사전 구축: Safety Monitor

- 구현: `core/safety_monitor.py`, 규칙: `config/safety_rules.yaml`, 테스트: `tests/test_safety_monitor.py`
- 규칙 16개(금칙어 7종, 개인정보 요청 6종, 비밀 유지 요구 1종, 개인정보 값 2종)와 예외 구절 9개를 초기값으로 넣었습니다. **운영 전에 교육·법무 담당자의 검토가 필요합니다.**
- 토큰 경계에서 잘린 단어("ki"+"ll"), SentencePiece `▁` 표시, 곡선 따옴표를 처리합니다.
- `match: word` 규칙은 "ass"가 "assistant"의 앞부분일 수 있으므로 다음 토큰에서 단어 경계를 확인한 뒤 확정합니다. 이 때문에 판정이 토큰 하나(약 80ms)만큼 늦어집니다. `match: prefix` 규칙(fuck, shit 등의 어간)은 바로 확정합니다.
- 테스트 58건이 통과했습니다(차단해야 할 문장 21개, 통과시켜야 할 문장 19개, 토큰 분할·경계·예외·말 끊김 동작).
- **Gateway 요구 사항:** Moshi는 전이중이라 턴 끝 신호가 없고, 말하지 않는 동안에는 텍스트 토큰도 오지 않습니다. 따라서 Gateway는 텍스트 토큰 없이 오디오 프레임이 2개(약 160ms) 이상 이어지면 `idle()`을 호출해야 합니다. 이 호출이 없으면 발화 마지막 단어("...you're so stupid" 뒤 침묵)의 위반을 확정하지 못합니다. 규격은 `docs/event_schema.md`에 적었고, 5단계 Gateway 구현에 반영합니다.
- 전화번호 규칙은 숫자 묶음 안의 공백을 허용하지 않습니다. 공백을 허용하면 "1, 2, 3, ... 10" 같은 숫자 세기 연습이 차단되기 때문입니다.

**CPU 처리 시간** (`bench/safety_latency.py`, `docs/reports/safety_latency_cpu.json`, 토큰 38,866개):

| 평균 | p50 | p95 | p99 | 최대 | 예산(토큰 간격) |
|---|---|---|---|---|---|
| 0.070 ms | 0.079 ms | 0.093 ms | 0.100 ms | 0.349 ms | 80 ms |

검사 자체의 지연은 무시할 수 있는 수준입니다. 차단 지연은 검사 시간이 아니라 "텍스트가 언제 도착하는가"(2절)와 `word` 규칙의 경계 확인 대기에 따라 정해집니다.

**아직 측정하지 못한 것:** 차단 성공률과 차단 전에 소리가 나간 비율은 실제 Moshi 출력이 있어야 측정할 수 있습니다(3단계 완료 기준). 숫자를 단어로 읽는 전화번호("five five five ...")는 아직 잡지 못합니다.

## 4. 4단계 사전 측정: ASR 병행 감시 (CPU)

### 4.1 언어 감지 (`bench/lang_probe_en.py`, `docs/reports/lang_probe_en.json`)

평가 음성은 두 종류입니다. 첫째는 Supertonic(CPU)으로 서버 안에서 합성한 영어 8문장, 한국어 4문장, 혼합 2문장입니다. 둘째는 한국어 Agent 1단계에서 쓴 직원 참조 녹음 8개입니다. 직원 녹음의 인식 원문은 결과 파일에 남기지 않았습니다.

| 설정 | 영어 합성 8개를 영어로 유지 | 한국어 합성 4개 감지 | 실제 한국어 녹음 7개 감지 |
|---|---|---|---|
| `en-US` 고정 | 8 | 0 (4개 모두 빈 결과) | 0 (6개 빈 결과, 1개는 영어 단어로 잘못 인식되어 영어로 판정) |
| `auto` | 8 | **4** | **7** |

- `clip05`는 `ko-KR` 설정(한국어 Agent 1단계)에서 빈 결과였고, `en-US`와 `auto` 모두에서 라틴 문자 약 170자로 인식되었습니다. 따라서 한국어 낭독이 아닐 가능성이 높아서 위 표에서 뺐습니다. 직접 들어서 확인해야 합니다.
- 혼합 문장: "선생님, apple 은 영어로 사과예요?"는 `auto`에서 한국어로 판정했습니다(의도대로입니다). "I like 떡볶이 very much."는 영어로 판정했고, 한국어 단어는 "to book you"로 인식되었습니다.
- `auto`의 영어 인식 결과는 언어 태그를 빼면 `en-US`와 8문장 모두 같았습니다. 따라서 자막 품질을 잃지 않습니다.

**결정 제안:** 영어 Agent의 ASR 병행 감시는 `language=auto`로 실행하고, `core/asr_monitor.py`의 판정 규칙(언어 태그 우선, 없으면 한글 비율 0.3 이상, 비영어 2회 연속이면 `language_mismatch`)을 사용합니다. `en-US` 고정은 한국어를 빈 결과로 버리므로 감지에 쓸 수 없습니다.

### 4.2 CPU 실시간 처리 속도 (영어, 8스레드)

`korean_agent/bench/asr_cpu_rtf.py`를 그대로 재사용했습니다(`--lang en-US`, 영어 합성 8문장, 총 24.4초). 원자료는 `docs/reports/asr_cpu_rtf_en_t8.json`에 있습니다.

| 조건 | 청크 지연 | RTF | 청크당 처리 |
|---|---|---|---|
| 오프라인(파일 전체) | - | 0.121 | - |
| lookahead 3 | 320 ms | 0.426 | 140 ms |
| lookahead 6 | 560 ms | 0.281 | 172 ms |

한국어 1단계(lookahead 3, RTF 0.437)와 거의 같습니다. 프롬프트 기준(RTF 1.0 미만)에 따라 **CPU 실행을 유지합니다.** 다만 이 값은 세션 1개 기준이고, 한국어 Agent의 ASR과 CPU를 함께 쓰는 상태는 7단계에서 다시 측정해야 합니다. 측정 중 서버 부하 평균은 1.3~6.3이었습니다.

## 5. Qwen Audio Agent 연동 (프롬프트 2.4절)

Moshi 서버는 Qwen Audio Agent의 `speech-to-speech` Provider 규격(OpenAI Realtime 호환 JSON)과 호환되지 않습니다. 1차 PoC는 자체 경량 Gateway로 진행할 것을 제안합니다. 근거와 어댑터 추정 비용은 `docs/version_check.md` 5절에 있습니다.

## 6. 문서와 실제의 차이

1. 프롬프트 4절의 저장소 이름은 `english-voice-agent/`이지만, 사용자 지시에 따라 `english-agent/`를 사용합니다. 하위 폴더 구성은 프롬프트대로 합니다.
2. Moshi PyTorch 서버는 한 번에 한 연결만 처리합니다. 동시 3·5세션 KPI를 측정하려면 서버 프로세스를 여러 개 띄워야 하고, 그만큼 GPU 메모리가 늘어납니다.
3. 서버에 Rust 도구가 없어서, 운영 백엔드(Rust/Candle INT8)를 쓰려면 2단계에서 `rustup`과 CUDA 빌드 환경을 설치해야 합니다.

## 7. GPU가 필요해서 진행하지 못한 것

- 1단계: Moshi BF16 구동과 브라우저 대화, 메모리·지연 측정 (약 24 GB 필요)
- 2단계: Rust INT8 전환, 텍스트·음성 시간 차이 실측
- 3단계 완료 기준: 차단 성공률·차단 지연 실측
